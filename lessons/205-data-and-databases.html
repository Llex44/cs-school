Under the hood: SQL and NoSQL optional

Relational databases are often called SQL databases, after the language you use to ask them questions (you'll write some in part 3). Document, key-value and vector stores are often lumped together as NoSQL.

The line is blurry. PostgreSQL can store JSON documents and, with the pgvector extension, vectors. MongoDB can combine documents from different collections. So the question is less "which product?" and more "which shape does most of my data have?"

Keys, copies and speed

Three ideas decide whether your data stays correct and fast as the shop grows: link things by keys instead of copying them, add indexes for the searches you do often, and change the database's shape carefully.

Copy it, or link it?

Two ways to remember Ana's email for her orders. One copies it into every order. The other stores it once and points at it.

Copied into every order

Linked by keys

Press Ana changes her email. The app's code will update the customer record, like most code does.

Every row gets a primary key: an ID that is unique and never changes, like customers.id = 1. When another table needs to refer to that row, it stores the ID in a foreign key column, like orders.customer_id. One fact lives in one place, so it can't drift out of sync.

Copying isn't always wrong. An order should keep the price the customer actually paid, even if the book's price changes later. The skill is knowing which facts should stay linked and which should be frozen at the moment they happened.

Under the hood: what an index really is optional

An index is a second, sorted copy of one column (like every order's email), with a pointer back to each row. Because it's sorted, the database can halve the search area at each step, like finding a word in a dictionary. Real databases use a structure called a B-tree to do this.

Indexes aren't free. Each one takes disk space, and every new order has to be added to it, which slows writing a little. Add them for columns you search, sort or join on often. When your AI says "I'll add an index on orders.customer_id", this is why.

Changing the shape later: migrations

A migration is a small script that changes the database's structure: add a column, rename one, remove one. AI tools write them all the time. Some can't be undone.

    Key terms

    The words your AI will use when it talks about data, in plain language.

    Database
    The place an app keeps what it needs to remember, so it survives restarts and can be shared by every user.
    Table, row, column
    A table holds one kind of thing (books). Each row is one of them. Each column is one fact about it (price).
    Primary key
    A unique ID for each row that never changes, like books.id.
    Foreign key
    A column that stores another table's ID, like orders.book_id. It links rows without copying them.
    Join
    Combining rows from two tables by matching keys, to answer questions like "who bought what".
    Query
    A question you ask the database. In relational databases it's written in SQL: SELECT … FROM … WHERE …
    Index
    A sorted lookup for one column that makes searches on it fast, at a small cost when writing.
    Migration
    A script that changes the database's structure. Dropping a column or table deletes that data for good.
    Backup
    A copy of the data you can restore. It only counts if you have tested restoring it.
    Document, key-value, vector
    Other shapes: nested records per thing, exact lookups by key, and search by similar meaning.
