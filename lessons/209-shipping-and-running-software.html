Under the hood: why rolling back takes seconds optional

A deploy doesn't edit the running app. It builds a complete new package of the app (a "build" or "release"), starts it, and then switches traffic over to it. The old build is kept.

So a rollback just switches traffic back to the previous build. No code is rewritten and nothing is rebuilt. Hosts like Vercel, Netlify, Render and Fly.io have a one-click rollback for exactly this reason.

Bigger teams go further: a canary release sends a new version to 5% of users first and watches the error rate before sending it to everyone.

    Local, staging, production

    Local
    Your computer, or the AI's workspace. Fast to change, only you see it, and full of settings that exist nowhere else."It works on my machine" is a local fact, not a promise.
    Staging
    A private copy set up like production, with fake data and test keys. You try each change here before customers see it.When the AI says "deployed to staging", nothing is public yet.
    Production
    The live app. Real customers, real data, real payments. Changes here should be boring, checked and easy to undo.When the AI says "deploying to prod", ask what checks it passed.

    Environment variables: same code, different settings

    The code is identical everywhere. What changes between local, staging and production lives in environment variables: named settings the host gives your app when it starts, like which database to use or which secret key to pay with. On your laptop they usually sit in a file called .env, which never goes into git.

    VariableLocal (.env file)StagingProduction
    DATABASE_URLA database on your laptopThe staging database, fake ordersThe real database, real orders
    PAYMENTS_KEYA test key: no real money movesMissingMissing
    SEND_TEXTSfalsefalsetrue: customers get "your tacos are ready"

    That's why the payments change worked locally and broke everywhere else: the new code needed PAYMENTS_KEY, and only your laptop had it. You'll fix that in part 3.

    A local TV show just featured Rosa's Tacos. At lunch, hundreds of people open the app every second. Each server can only answer so many visitors at once. Past that, pages slow down, then fail. You can add servers, add a cache, or fix the slow part, and each choice has a price.

    Under the hood: serverless and managed hosting optional

    Most small apps today don't manage servers directly. Managed hosts and serverless platforms start copies of your app on demand and charge for what you use. That's autoscaling built in.

    The trade-offs don't go away. A traffic spike still costs money, so set a spending limit and a billing alert. And a slow database query is slow no matter how many copies of your app are running.

    Four ways to handle more visitors

    MoveWhat it doesCostWatch out
    Fix the slow partFind the one query or function doing too much work and make it faster.Some work, then freeAlways look here first. It's often the whole problem.
    CacheKeep a ready-made copy of pages or data that rarely change.SmallCached data can be stale, like an old price.

    Scale upMove to one bigger, faster machine.Big jumpsThere's always a biggest machine.

    Autoscaling does the scaling out for you: more servers when it's busy, fewer when it's quiet, so you only pay for the rush while it's happening.

    Knowing when it breaks: logs, metrics, alerts

    You can't watch your app all day. These three do it for you.

      Cheat sheet

      The words you'll hear once your app is live, and what to listen for.

      TermIn plain wordsWhen the AI says…
      DeployPut a new version of the code where it runs."Deploying to production." Ask: did it go through staging first?
      StagingA private rehearsal copy of the live app."It's on staging." Try it there yourself.
      ProductionThe live app with real users."Pushed to prod." Is someone watching it for the next hour?
      RollbackSwitch back to the previous build."Rolling back." The right first move when prod breaks.
      Environment variableA setting, often a secret, given to the app by the host."Add it to your .env." Never paste keys into the code.
      Scale out / upMore servers / a bigger server."Let's add servers." Ask what's actually slow first.
      CacheA ready-made copy of something slow to make."I'll cache it." Ask how long it can be out of date.
      AutoscalingServers added and removed automatically with traffic."It autoscales." Ask for a maximum and a spending limit.
      Logs · metrics · alertsThe diary, the numbers, and the ping when numbers go bad."Checking the logs." Good: that's where the clues are.
