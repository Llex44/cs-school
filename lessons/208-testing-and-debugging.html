Under the hood: why "3.50" + "7.00" made "03.507.00" optional

In JavaScript, + means two different things. Between numbers it adds: 3.5 + 7 is 10.5. If either side is text (a string), it glues them together: "3.5" + "7" is "3.57".

Data that arrives from a server, a form or a web address is often text, even when it looks like a number. That's why Number(item.price) fixes it: it turns the text "3.50" into the number 3.5 before adding.

To see the console on a real site: in Chrome or Edge, right-click the page, choose Inspect, then the Console tab. Errors on the server side live in your hosting logs instead (course 209).

How to read an error

Errors look scary, but they're always built the same way. Here's the one you just met.

Uncaught TypeError1: total.toFixed is not a function2 at formatPrice (cart.js:11)3 at showCheckout (checkout.js:6)4 at checkoutButton.onclick (shop.js:21)
1The type
TypeError means a value was the wrong kind, like text where a number was needed. Other common ones: ReferenceError (a name that doesn't exist, often a typo) and SyntaxError (code that isn't valid, like a missing bracket).
2The message
What went wrong, in the computer's words. "total.toFixed is not a function" means: total doesn't have a toFixed, so total isn't the number we expected.
3Where it crashed
The top line of the stack trace: the function, the file and the line number. cart.js:11 means file cart.js, line 11. Start reading here.
4How it got there
Each line below is the function that called the one above it, all the way back to the click. The real cause is often further down this trail than the crash.

Tests: code that checks code

A test is a tiny program that runs your code with a known input and checks the answer. A computer can run hundreds of them in seconds, every time anything changes. That's how you notice when an AI "improvement" quietly breaks something that used to work.

Three kinds of tests

Unit tests check one small piece, like the delivery function, by itself. They run in milliseconds and point straight at the broken line. Most of your tests should be these.

Integration tests check that pieces work together, like coupon plus delivery at checkout, or the code plus the database.

End-to-end tests drive a real browser like a robot customer: open the site, click Add, click Check out. They catch wiring problems nothing else can, but they're slow and fragile, so keep a few for the most important journeys.

Green doesn't mean correct. Passing tests only prove that the things someone thought to check still work. When the AI says "all tests pass", ask: "Do the tests cover what I just changed?"
Under the hood: what a test file looks like optional

Most languages have a test tool: Jest or Vitest for JavaScript, pytest for Python, Playwright or Cypress for end-to-end tests. They all read much the same:

test('exactly $25 gets free delivery', () => { expect(delivery(25)).toBe(0); });

A name that says what should be true, some code to run, and an expectation. A test you add after fixing a bug is called a regression test: it makes sure the same bug can't sneak back in later.

Tests usually run automatically on every pull request. This is called continuous integration (CI). When an AI tool says "CI is red", a test failed on its branch.

    How to read a test

    test('big orders ship free', () => { expect(delivery(40)).toBe(0); });

    Read it out loud: "Test that big orders ship free. Expect delivery of 40 to be 0."

    expect(…) is what the code actually gives. toBe(…) is what it should give. The right answer comes from the promise, never from what the code happens to do.

    Under the hood: why the edge matters optional

    > means "greater than". >= means "greater than or equal to". They agree on every amount except exactly 25. Bugs love these edges, so good tests check right on the line and just either side of it.

    Ask your AI for "boundary tests" or "edge cases" and it will add tests like $24.99, $25.00 and $25.01.
