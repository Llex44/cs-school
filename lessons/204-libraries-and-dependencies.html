Why a tiny block matters

Packages you add yourself are direct dependencies. The packages they need, and the ones those need, are transitive dependencies. You never chose them, but your app runs their code, and trusts every one of their authors.

A real app often has hundreds of these blocks. Most are great: well tested, free and maintained by kind strangers. That's why packages are worth using. But it means every package you add brings its whole tower with it.

Under the hood: famous collapses optional

left-pad, 2016. An 11-line package that added spaces to the start of text. Its author removed it from npm after a dispute, and thousands of projects that depended on it, often without knowing, stopped building. npm then changed its rules so popular packages can't simply be removed.

event-stream, 2018. A tired maintainer handed a popular package to a helpful stranger. The stranger added a hidden dependency designed to steal from one bitcoin wallet app.

colors.js, 2022. The author of a popular package deliberately published a version that printed gibberish forever, breaking the apps that used it.

Three ways a package can hurt you

Look-alike names

Typosquatting: attackers publish packages one letter away from popular ones, like reactt or expres, and wait for a typo. AI tools can invent package names too, and attackers sometimes register those names.

Abandoned packages

Nobody has updated it in years. Bugs and security holes stay unfixed, and it may stop working with newer tools. Worse, someone new can take it over.

Known holes

A vulnerability is a security bug that attackers can use. They're found in good packages too, and fixed in new versions. Tools like npm audit check yours against a public list. You'll run it in part 3.

Before you add a package, ask

  1. Do I need it? Could a built-in feature or ten lines of code do the job?
  2. Is it the right name? Check the spelling, and that it's the package everyone means.
  3. Is it alive? Lots of weekly downloads, a recent update, more than one maintainer, a real source code link.
  4. How big is it? Check its size and how many packages it brings along. Every one is more to download and more to trust.
  5. Can I use it? The license says what you're allowed to do. MIT, Apache and BSD are easy to use in almost anything. GPL and AGPL come with conditions about sharing your own code, so check first.

Ranges: which versions will you accept?

In package.json you don't have to name one exact version. You can write a range, and npm installs the newest version that fits it.

Rosie's package.json says

"super-date-picker": "4.2.1"

Versions on the registry

Green versions fit the range. npm installs the starred one.

Under the hood: versions that start with 0 optional

A package on 0.x, like color-mix-lite 0.9.1, hasn't promised a stable design yet. Anything may change. So npm is stricter: ^0.9.1 only accepts 0.9.x, never 0.10.0.

Versions like 5.0.0-beta.2 are pre-releases: test versions that ranges skip unless you ask for them by name.

The shopping list and the receipt

If package.json only lists ranges, how does everyone end up with the same versions? With a second file.

package.json

The shopping list. You and your AI edit it.

// what Rosie is happy to accept "dependencies": { "super-date-picker": "^4.2.1", "confetti-burst": "^2.0.0" }

Only your direct dependencies, with ranges.

package-lock.json

The receipt. npm writes it for you.

// exactly what was installed "node_modules/super-date-picker": { "version": "4.4.1", … }, "node_modules/pad-start-lite": { "version": "1.0.3", … }

Every package in the tower, even the deep ones, with its exact version.

This lockfile is why going back to pad-start-lite 1.0.3 fixed Rosie's app in part 1: it pins the whole tower, so every computer installs the same blocks.

  • Commit both files to git (course 203). Never delete the lockfile to "fix" something.
  • npm install installs what the lockfile says, and updates it when you add or change a package.
  • npm ci installs exactly what the lockfile says, or stops with an error. Servers use it when they build your app (course 209).

    Tower health

    Under the hood: install scripts optional

    A package can include a postinstall script: a command npm runs on your computer the moment you install it. Good packages use this to set themselves up. A malicious one can read your files, including secrets like API keys, and send them away.

    That's why you check a package before installing it, not after. If you ever install a bad one, remove it and change any secrets that were on that computer.
