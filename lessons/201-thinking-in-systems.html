Sketch any app in four steps

  1. Who uses it? Draw the people and their devices: customers on phones, Rosie in the kitchen.
  2. What does it remember? Draw a box for each place data lives: the database, image storage.
  3. What does it rent? Draw each outside service: payments, email, maps, AI models.
  4. Who needs a message from whom? Draw a wire for each, and note what travels on it.

Then point at each box and ask: what happens if this one is down? That's part 2.

Under the hood: every wire is a request and a response optional

Each wire carries two messages: a request ("please charge $18.50") and a response ("approved"). Usually the sender waits for the response before it moves on. That waiting is why one slow part, far away, can make your whole app feel slow.

The agreed format for these messages is called an API. Course 206 APIs & integrations takes them apart.

What customers can do

Blast radius: nothing broken

    Failures travel along the wires. When a part goes down, everything that needs it goes down too. How far the damage spreads is called its blast radius.

    A single point of failure is a part whose failure stops everything. In Rosie's app, that's the API server and the database: every order passes through both.

    A queue is a waiting line between two parts. The sender drops a job in and moves on. The receiver picks jobs up when it can, and retries if it has to. Use one whenever the customer doesn't need to wait for the work: emails, receipts, resizing photos, reports.

    Under the hood: how real apps avoid single points of failure optional

    Real apps run two or more copies of the API server, with a load balancer in front that spreads requests between them and skips a copy that stops answering. Databases get automatic backups, and often a standby copy that can take over.

    Hosting platforms do much of this for you, and each extra copy costs money, so it's a choice, not a default. Course 209 Shipping & running software covers it.

    A bottleneck is the part that runs out of room first. The whole app can only go as fast as its slowest part on the path, so speeding up any other part changes nothing.

    A feedback loop is a reaction that feeds its own cause. Instant retries turn an overload into a pile-up: failures cause retries, and retries cause more failures. Engineers call it a retry storm, and it's how a busy lunch hour becomes a full outage.

    Retry with backoff waits longer after each failure (1 second, then 2, then 4…) and gives up after a few tries. That gives the struggling part room to recover.

    Under the hood: retries that can't charge twice optional

    If a charge request times out, you don't know whether it went through. Retrying blindly can bill the customer twice. Payment providers solve this with an idempotency key: a unique ID sent with each charge. If the same ID arrives twice, the provider only charges once.

    When an AI adds retries around anything that spends money or sends messages, ask it how it avoids doing the thing twice.

        Under the hood: status, logs and alerts optional

        A health check asks each part "are you there?" every few seconds. It's quick, but shallow: a part can answer and still fail at its real job.

        Logs are each part's diary: one line per thing it did, with the time. Metrics are numbers over time, like response time. Alerts message you when a number crosses a line, so you hear about problems before your customers text you.
