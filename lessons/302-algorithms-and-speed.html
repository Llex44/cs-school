Race: one by one vs halving

Same secret number, same pace: one check per tick. Who finds it first?

You just used binary search

Guessing the middle rules out half of what's left every time: 1,000, then 500, 250, 125… down to 1 in about 10 guesses. That strategy is called binary search. Checking one by one is called linear search.

How many itemsOne by one, worst caseHalving, worst case
1,0001,000 checks10 checks
1 million1,000,000 checks20 checks
1 billion1,000,000,000 checks30 checks

Every time the data grows 1,000 times bigger, halving needs only 10 more checks. There's one catch: halving only works when the data is sorted. If the numbers were shuffled, "higher" and "lower" would tell you nothing. That's why sorting is one of the most important jobs a computer does.

Under the hood: where halving hides in real software optional

A database index keeps a column sorted in a tree shape so the database can halve its way to a row instead of reading the whole table. When an AI says "add an index on email", this is what it means.

git bisect uses the same trick to find which of 1,000 commits introduced a bug: test the middle commit, then keep halving. About 10 tests instead of 1,000.

The math name for "how many times can I halve n until 1 is left" is log₂ n, the logarithm. log₂ of 1,000 is about 10. log₂ of 1 billion is about 30.

The name for growth: Big-O

Programmers describe how work grows with Big-O. O(n), said "order n", means the work grows in step with the data: twice the users, twice the work. O(n²) means twice the users, four times the work. Big-O ignores small details, like whether a step takes 1 or 2 microseconds, because at scale the growth always wins.

When an AI says "this is O(n²)", translate it as: fine on test data, trouble with real users.

The slow pattern AI writes most: a loop inside a loop

Here's code an AI might write to show each order with its customer's name. For every order, it searches the whole customer list.

for (const order of orders) { // n orders for (const c of customers) { // × n customers if (c.id === order.customerId) … } }

It often hides in one tidy line. .find(), .filter() and .includes() are loops too, so this is also n × n:

orders.map(o => customers.find(c => c.id === o.customerId) )

With 1,000 of each, that's up to a million checks. With 100,000 of each, 10 billion.

Under the hood: why merge sort grows slower optional

Bubble sort compares nearly every pair of books: about n × n ÷ 2 comparisons. Merge sort splits the shelf in half again and again (that's log₂ n levels), and each level does about n comparisons while merging. Total: about n × log₂ n.

For 1 million books that's roughly 500 billion comparisons for bubble sort versus 20 million for merge sort. Real programming languages use merge-sort-style methods in their built-in sort(), so when an AI writes its own sorting loop, ask why.

    Under the hood: why a Map lookup is one step optional

    A Map turns each key (like "c417") into a number that says exactly which slot to look in. This is called hashing. No searching needed, so a lookup takes about the same time with 10 customers or 10 million. Course 303 shows how it works.

    Building the Map costs one pass over the customers. After that, every lookup is cheap. One loop plus one loop is 2n, which grows far slower than n × n.
