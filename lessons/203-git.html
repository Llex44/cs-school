Under the hood: the staging area optional

Real git has one extra step before a commit. First you stage the changes you want (git add), then you commit them. It's like packing items into a box before you seal and label it. This lets you save some changes now and leave others for later.

    What's inside a commit

    This is your latest save point, printed the way git prints it.

    An ID
    A unique fingerprint made from the contents, like 3f9a2c1. You and the AI can point to any commit by its ID.
    Who and when
    The author and the time. Useful when you ask "what changed since Tuesday?"
    A message
    A short note on what changed and why. Good messages make the history readable.
    A snapshot
    The complete state of every file at that moment, so you can return to it exactly.
    A parent
    A link to the commit before it. The chain of parents is your project's history.

    Branches: a new line for every experiment

    A branch is a separate line of history where you can try an idea without touching the working version. Main is the line everyone relies on. When an idea works, you merge its line back into main.

    Your task

    1. Start a new branch.
    2. Commit twice on your branch.
    3. Switch back to main.
    4. Switch to your branch again and merge it into main.

    The glowing dot and the dark label mark HEAD, which means "you are here". New commits always land where HEAD is.

    Good AI coding tools work this way on bigger changes. They create a branch, commit there, and ask you to review before anything reaches main.

    Under the hood: pull requests optional

    On GitHub you usually don't merge a branch directly. You open a pull request (PR), a page that says "here are my branch's changes, please review and merge them." Teammates or AI reviewers comment, automated tests run, and only then does someone click Merge.

    When an AI tool says "I opened a PR", its work is waiting on a branch for your approval. Nothing has changed on main yet.

    When two lines change the same thing: merge conflicts

    If two branches change the same line in different ways, git can't guess which one you want. It stops and marks the spot. This is a merge conflict, and it's normal.

      Under the hood: your computer vs GitHub optional

      Git is the tool that keeps history on your computer. GitHub is a website that stores a shared copy so other people, and AI agents in the cloud, can work on it.

      git push sends your new commits up to GitHub. git pull brings down commits other people made. When an AI says "I pushed the branch", your team can now see the work.

      Cheat sheet

      The commands you'll see AI tools run most, and what to listen for.

      CommandIn plain wordsWhen the AI says…
      git statusWhat has changed since the last save point?"Let me check the state of the repo."
      git addPut these changes in the next save point."Staging the changes."
      git commit -m "…"Make a save point with a note."Committed: Add login page." Check that the message is specific.
      git logShow the history."Looking at recent commits."
      git switch -c nameStart a new branch and move to it."I'll work on a new branch." A good sign.
      git merge nameBring a branch's work into this one."Merging into main." Did you review it first?
      git push / git pullSend commits to GitHub, or bring others' commits down."Pushed the branch and opened a PR."
      git revertUndo a commit by adding an opposite commit."I'll revert that change." Safe, because history is kept.
      git push --forceOverwrite the shared history.Stop and ask why. On main, this can erase teammates' work.
